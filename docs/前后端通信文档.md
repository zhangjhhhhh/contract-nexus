# 前后端通信开发文档

## 目标

当前前端使用 `src/mock` 静态数据和 Zustand 本地持久化模拟后端。下一步开发目标是把这些本地数据操作逐步替换为真实后端接口调用，同时保持现有页面、路由、表单校验和交互体验不变。

本文不假设后端具体技术栈，默认采用 REST API + JSON 作为前后端通信契约。

## 总体改造思路

建议按以下顺序开发：

```text
接口契约确认 -> 后端接口实现 -> 前端 API 层封装 -> 替换 Zustand 动作 -> 联调测试 -> 删除或降级 Mock 数据
```

不要一开始直接删除 Mock 数据。建议先保留 Mock 数据作为本地兜底，等接口稳定后再清理。

## 第一步：统一接口基础约定

前后端先约定统一响应格式。

建议格式：

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

约定规则：

- `code = 0` 表示成功。
- `code != 0` 表示业务失败。
- HTTP 401 表示未登录或登录过期。
- HTTP 403 表示无权限。
- HTTP 500 表示服务端异常。
- 日期统一使用 `YYYY-MM-DD` 或 `YYYY-MM-DD HH:mm:ss`。
- ID 字段保持字符串类型，避免前端处理大数字精度问题。

## 第二步：配置接口地址

前端新增环境变量，不要把接口地址写死在业务组件里。

建议：

```text
frontend/.env.development
VITE_API_BASE_URL=http://127.0.0.1:8080/api

frontend/.env.production
VITE_API_BASE_URL=/api
```

注意：

- `.env` 中不要放密码、密钥、数据库连接串。
- 如果使用 Cookie 登录，开发环境需要后端配置 CORS 和凭证。
- 如果使用 Token 登录，Token 只由登录接口返回，前端不要硬编码。

## 第三步：新增前端 API 层

建议新增目录：

```text
frontend/src/api/
  http.ts
  auth.ts
  contracts.ts
  customers.ts
  users.ts
  roles.ts
  logs.ts
```

职责划分：

- `http.ts`：统一封装 `fetch` 或 `axios`，处理 baseURL、请求头、错误码、登录过期。
- `auth.ts`：登录、注册、退出、当前用户。
- `contracts.ts`：合同列表、详情、起草、分配、会签、定稿、审批、签订。
- `customers.ts`：客户增删改查。
- `users.ts`：用户增删改查。
- `roles.ts`：角色和权限。
- `logs.ts`：日志查询和导出。

页面组件不要直接调用 `fetch`，只调用 API 层或 Zustand action。

## 第四步：登录与会话

建议接口：

| 方法 | 地址 | 说明 |
| --- | --- | --- |
| `POST` | `/auth/login` | 登录 |
| `POST` | `/auth/register` | 注册 |
| `POST` | `/auth/logout` | 退出 |
| `GET` | `/auth/me` | 获取当前登录用户 |

登录返回建议：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "user": {
      "id": "U001",
      "name": "admin",
      "roleIds": ["admin"]
    },
    "permissions": ["dashboard:view", "system:user"]
  }
}
```

两种会话方案二选一：

| 方案 | 说明 |
| --- | --- |
| Cookie Session | 后端设置 HttpOnly Cookie，前端请求带 `credentials`。安全性较好。 |
| Bearer Token | 登录接口返回 Token，前端放在内存或安全存储中，请求头带 `Authorization`。 |

建议优先使用 Cookie Session。真实系统不建议把密码或长期 Token 暴露在 localStorage。

## 第五步：合同接口

建议接口：

| 方法 | 地址 | 说明 |
| --- | --- | --- |
| `GET` | `/contracts` | 合同列表，支持查询条件 |
| `GET` | `/contracts/:id` | 合同详情 |
| `POST` | `/contracts` | 起草合同 |
| `PUT` | `/contracts/:id` | 修改合同基础信息 |
| `DELETE` | `/contracts/:id` | 删除合同 |
| `POST` | `/contracts/:id/assign` | 管理员分配会签、审批、签订人员 |
| `POST` | `/contracts/:id/countersign` | 提交会签意见 |
| `POST` | `/contracts/:id/finalize` | 提交定稿内容 |
| `POST` | `/contracts/:id/approve` | 提交审批结果 |
| `POST` | `/contracts/:id/sign` | 录入签订信息 |
| `GET` | `/contracts/:id/processes` | 查询合同流程 |

列表查询参数建议：

```text
GET /contracts?keyword=设备&status=approving&beginDate=2026-05-01&endDate=2026-05-31&page=1&pageSize=10
```

列表返回建议：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "list": [],
    "total": 15,
    "page": 1,
    "pageSize": 10
  }
}
```

## 第六步：流程状态由后端控制

当前前端会在 Zustand 中修改合同状态。接入后端后，合同状态必须由后端控制。

前端只提交动作：

- 起草合同。
- 分配人员。
- 提交会签意见。
- 提交定稿。
- 提交审批结果。
- 录入签订信息。

后端负责判断：

- 当前合同是否允许执行该动作。
- 当前用户是否是该流程节点处理人。
- 当前流程是否全部完成。
- 下一状态应该是什么。
- 审批拒绝后是否终止流程。

前端提交成功后重新拉取合同列表或合同详情。

## 第七步：客户接口

建议接口：

| 方法 | 地址 | 说明 |
| --- | --- | --- |
| `GET` | `/customers` | 客户列表 |
| `GET` | `/customers/:id` | 客户详情 |
| `POST` | `/customers` | 新增客户 |
| `PUT` | `/customers/:id` | 修改客户 |
| `DELETE` | `/customers/:id` | 删除客户 |

删除客户时，后端需要校验客户是否已被合同引用。若已引用，返回业务错误。

## 第八步：用户、角色、权限接口

建议接口：

| 方法 | 地址 | 说明 |
| --- | --- | --- |
| `GET` | `/users` | 用户列表 |
| `POST` | `/users` | 新增用户 |
| `PUT` | `/users/:id` | 编辑用户 |
| `DELETE` | `/users/:id` | 删除用户 |
| `PUT` | `/users/:id/roles` | 给用户分配角色 |
| `GET` | `/roles` | 角色列表 |
| `POST` | `/roles` | 新增角色 |
| `PUT` | `/roles/:id` | 编辑角色 |
| `DELETE` | `/roles/:id` | 删除角色 |
| `GET` | `/permissions` | 权限列表 |

权限建议由后端返回，前端不要写死真实权限结果。当前 `permissionGroups` 可以先作为前端展示分组，后续可改为接口返回。

## 第九步：日志接口

建议接口：

| 方法 | 地址 | 说明 |
| --- | --- | --- |
| `GET` | `/logs` | 日志列表 |
| `GET` | `/logs/export` | 导出 CSV |

查询参数：

```text
GET /logs?keyword=审批&beginDate=2026-05-01&endDate=2026-05-31&page=1&pageSize=10
```

真实系统中日志应由后端记录，前端不再调用 `addLog` 手动写日志。

## 第十步：附件上传

当前前端只校验附件文件名。接入后端后建议拆成两步：

1. 上传附件。
2. 起草合同时提交附件 ID。

建议接口：

| 方法 | 地址 | 说明 |
| --- | --- | --- |
| `POST` | `/files` | 上传附件，使用 `multipart/form-data` |
| `GET` | `/files/:id` | 下载或预览附件 |

后端必须校验：

- 文件类型。
- 文件大小。
- 文件名安全性。
- 存储路径。
- 当前用户是否有访问权限。

## 第十一步：前端替换顺序

建议按风险从低到高替换：

1. 登录、注册、当前用户接口。
2. 客户列表接口。
3. 合同查询接口。
4. 合同起草接口。
5. 合同流程接口。
6. 管理员分配接口。
7. 用户、角色、权限接口。
8. 日志查询和导出接口。
9. 附件上传接口。

每替换一个模块，保留页面交互不变，只替换数据来源。

## 第十二步：Zustand 改造方式

当前 `appStore.ts` 同时承担数据存储和业务动作。接入后端后建议调整为：

- store 只存当前用户、权限、少量页面缓存。
- 业务数据由 API 拉取。
- 列表页进入时请求后端。
- 提交成功后重新请求列表或详情。

建议保留：

- `session`
- `currentUser`
- `permissions`
- `showToast`
- `confirm`

建议移除或降级：

- 本地 `contracts`
- 本地 `customers`
- 本地 `users`
- 本地 `logs`
- 本地流程状态计算

## 第十三步：联调检查清单

每个接口联调时检查：

- 请求地址是否正确。
- 请求方法是否正确。
- 参数名是否和后端一致。
- 日期格式是否一致。
- 成功响应是否能刷新页面数据。
- 业务失败是否显示 Toast。
- 401 是否跳登录。
- 403 是否跳无权限页。
- loading 状态是否正常关闭。
- 空数据是否显示空状态。
- 分页总数是否正确。

## 第十四步：推荐开发节奏

第一阶段：

```text
后端完成登录、当前用户、权限、客户列表、合同列表接口。
前端完成 API 层和登录态改造。
```

第二阶段：

```text
后端完成合同起草、分配、会签、定稿、审批、签订接口。
前端替换合同流程相关 Zustand 动作。
```

第三阶段：

```text
后端完成用户、角色、权限、日志、附件接口。
前端替换系统管理和日志模块。
```

第四阶段：

```text
删除无用 Mock 写操作，仅保留演示种子数据或测试 fixture。
补充接口异常、权限失效、分页筛选、上传失败等测试。
```
